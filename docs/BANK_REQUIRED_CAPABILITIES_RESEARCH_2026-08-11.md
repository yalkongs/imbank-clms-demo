# CLMS 은행 요구기능 갭 연구 및 실행 권고

> 기준일: 2026-08-11 (Asia/Seoul)  
> 기준 커밋: `2a56feb851b94ed528642d5b49d97869a2d21ff0`  
> 대상: iM뱅크 기업여신 CLMS PoC의 은행 파일럿·운영 전환 준비도  
> 판정: **분석·의사결정 PoC로는 강함 / 통제된 은행 파일럿에는 조건부 / 운영계 전환에는 P0 보강 필요**

이 문서는 현재 코드·데이터를 다시 검증하고, 국내 은행 실무, iM뱅크의 시중은행 전환 특성, 2026년 8월 현재 금융당국의 정책·감독 방향을 대조해 “추가로 무엇을 구현해야 실제 가치가 생기는가”를 정리한 실행 문서다. 법률의 특정 조항이 특정 UI나 테이블을 직접 요구한다고 단정하지 않으며, 실제 적용 전에는 iM뱅크 준법·법무·리스크·회계·정보보호 조직의 확인이 필요하다.

## 1. 결론

현재 CLMS에 가장 필요한 것은 새 대시보드가 아니다. 다음 두 층을 하나의 통제된 흐름으로 연결하는 것이 우선이다.

1. **승인 이후 실행층**: 승인조건·약정 → 조건선행(CP) 충족 → 담보권·보증 유효성 확인 → 계정계 실행 → 한도·신용공여·회계 대사
2. **전 과정 통제층**: 세부 권한·직무분리 → KYC/KYB·AML → 책무·통제증거 → 데이터 계보 → 감사·복구

현재 구현은 재무·등급·RAROC·EWS·건전성분류·ECL·Workout을 폭넓게 보여준다. 반면 은행이 실제 돈을 내보내기 전에 반드시 확인하고, 실패 시 멈추며, 사후에 재현해야 하는 통제는 아직 서로 연결되지 않았다. 따라서 다음 개발의 성공 기준은 “화면 수”가 아니라 아래 질문에 `예`라고 답할 수 있는지다.

- 승인 당시 사용한 고객·그룹범위·재무·등급·모델·규칙·가격·예외·결재자를 다시 재현할 수 있는가?
- KYC, 전결권, 직무분리, 승인조건, 조건선행, 법정한도 또는 담보권 중 하나라도 미충족이면 실행이 기술적으로 차단되는가?
- 재시도나 장애가 중복 실행을 만들지 않고, 승인·계정계·익스포저·GL 상태가 대사되는가?
- 중요 통제가 수행자·점검자·책임임원·증빙·결함·시정조치까지 이어지는가?

## 2. 조사 방법과 근거 등급

- 현재 커밋의 승인, 단계전이, 권한, covenant waiver, 자동화 실행, 감사, 스냅샷, 규칙, 마이그레이션 코드를 정적 검토했다.

- 금융위원회, 금융정보분석원, 국가법령정보센터, iM뱅크의 공식 자료만 규제·정책·은행 특성의 근거로 사용했다.

AGY CLI의 [2026-08-11 독립평가 입력·출력](../reviews/agy_clms_bank_capability_assessment_2026-08-11.md)을 현재 검증사실로 다시 수행했다. AGY도 승인·위원회·회피, KYC/AML, 실시간 익스포저와 outbox, EDMS 증빙, 담보권 완성, 규칙/RAROC 일관성, 세부 권한·감사를 우선 기능으로 제시했다. 다만 AGY 출력은 규제 근거가 아니라 교차검토 의견으로만 사용했고, 모든 현재 결함은 코드·DB·임시 DB 실증으로 별도 확인했다.

### 3.2 이번 개선에서 실제로 해결된 것

- 승인금액을 작게 보내 전결권을 우회하던 결함은 해소됐다. 전결권은 승인금액이 아니라 **신청금액 전체**로 판단한다(`backend/app/api/applications.py:909-937`).
- 승인금액·금리·기간 컬럼이 추가됐고 승인 트랜잭션에서 저장한다(`applications.py:945-959`).
- 승인자와 승인권한은 클라이언트 문자열이 아니라 인증 사용자에서 결정한다(`applications.py:868-889`).
- 승인, 업종한도 예약, 판단자료 스냅샷, 핵심 감사기록이 하나의 트랜잭션 경계로 묶였다.
- 익명 쓰기는 전역 미들웨어에서 차단되고, 전결권 회귀시험이 추가됐다.

이는 의미 있는 개선이다. 다만 **통제의 구성요소가 생긴 것**과 **은행 업무흐름이 완성된 것**은 다르다.

| IFRS 9 시나리오·overlay·개별평가·GL 대사 연계 | CLMS 판단과 중앙 ECL/회계 결과의 차이를 설명·승인·재현 |
| 담보 재평가·보험·권리침해·말소/대체, 보증기관 연계 | 유효담보가액과 채권보전 상태를 실행·사후관리와 연결 |
| 회수·법적절차·경매·대위변제·상각·NPL 매각 | Workout 분석을 실제 회수 사건과 회계처리로 확장 |
| 배치 통제·관측성·RTO/RPO·DR·백업복구 시험 | 생산운영의 장애 탐지, 복구, 외부서비스 의존성 관리 |

### 5.3 P2 — 포트폴리오와 실제 사용범위가 확인된 뒤 확장

- PF 사업장별 자기자본 납입, 공정률, 분양률, 원가, 트랜치, 자금용도, 재구조화 관리
- AI/모델 inventory, 승인, 배포, drift, 설명, 이의제기, human review. 현재 심사의견 초안이 규칙 기반이라면 AI 규율을 과도하게 선구현하지 말고 실제 모델 사용위험에 비례해 적용한다.
- 기후·녹색금융 적격성, 자금용도, 성과, 그린워싱 통제와 기후 스트레스
- 지급보증·L/C·무역금융 등 난외상품의 별도 생애주기
- 시행 전 PF 정책안은 현행 규칙으로 hard-code하지 않고 정책 시뮬레이션 버전으로 관리한다.

## 6. P0 기능의 최소 설계와 인수기준

### 6.1 여신 워크플로·승인 오케스트레이션

**필요 기능**

- 상품·금액·등급·담보·예외에 따라 결정되는 버전형 승인경로
- 현재 상태별 허용 전이와 필수 산출물·검토·gate
- 기안자·심사자·승인자 분리, 동일인/동일조직 제약, 위임·대결·회피
- 위원회 안건, 정족수, 개별표결, 반대의견, 이해상충, 회의결론
- 낙관적 잠금, 요청 멱등키, 중복 승인 차단, 업무시간과 사건시간 분리

**최소 인수기준**

1. 선행단계·필수문서·필수검토가 없으면 승인 API가 4xx로 거부한다.
2. maker는 checker가 될 수 없고, 위임·대결은 권한·기간·사유가 유효해야 한다.
3. 조건부 승인 뒤 상위 승인자가 정상적으로 이어서 결재하며 ID 충돌이 없다.
4. 동시 승인 요청 중 하나만 성공하고 나머지는 명확한 충돌 응답을 받는다.
5. 과거 건은 당시 workflow·전결규정 버전으로 재현된다.

### 6.2 IAM·세부 권한·민감정보 통제

**필요 기능**

- 은행 SSO/OIDC 또는 사내 IAM, MFA, 세션 철회와 퇴직·전보 즉시 반영
- 역할뿐 아니라 부점, 담당기업, 포트폴리오, 금액, 상품, 지역, 데이터 민감도 기반 ABAC
- 읽기와 쓰기 모두에 대한 자원범위 통제, 필드 마스킹, 다운로드·대량조회 통제
- break-glass 승인, 만료, 사후검토와 서비스 계정·배치 계정 분리
- `approved_by`, `checked_by` 같은 actor 문자열을 요청에서 제거하고 인증 컨텍스트만 사용

**최소 인수기준**

1. 일반 직원은 waiver, 시설동결, 등급변경, 최종승인을 실행할 수 없다.
2. 다른 부점·담당외 고객의 민감정보는 조회·CSV·API에서 같은 정책으로 제한된다.
3. 권한 변경과 긴급권한 사용이 실시간 반영되고 감사증거로 남는다.

### 6.3 KYC/KYB·AML·UBO gate

금융정보분석원은 대출·보증·팩토링도 고객확인 대상에 포함하고, 신원·실제소유자·거래목적·자금원천 확인 및 위험기반 EDD를 설명한다. CLMS가 AML 엔진을 복제할 필요는 없지만, 여신의 승인·실행 시점에 유효한 결과를 확인하고 차단할 책임은 업무흐름에 있어야 한다.

**필요 기능**

- 법인식별·중복통합, 버전형 지분/지배구조와 UBO 근거 참조
- CDD/EDD 상태, 위험등급, 유효기한, screening 결과 참조 ID와 조회시각
- 중요한 고객·소유구조·거래목적 변경 시 재확인 trigger
- 미완료·만료·고위험 미승인 시 승인 또는 실행 hard stop
- STR 상세·혐의정보는 CLMS에 복제하지 않고 최소상태와 접근통제만 유지

**최소 인수기준**

1. CDD가 만료되거나 UBO 확인이 미완료면 신규 실행이 차단된다.
2. AML 원천시스템 장애 시 fail-open이 아니라 정의된 예외승인·만료가 적용된다.
3. CLMS에는 조회근거와 상태만 남고 고도의 AML 민감정보는 노출되지 않는다.

### 6.4 승인조건·문서·담보권·실행 전 gate

**필요 기능**

- 승인조건을 `condition_id, 유형, 책임자, 기한, 필수여부, 충족기준, 증빙, 검증자, 상태, 버전`으로 구조화
- 조건선행(CP), 조건후속(CS), covenant, 고객통지, 법무검토의 단일 의무모델
- EDMS 문서 ID, 문서종류, 버전, 진위확인, 만료, 전자서명·법무 승인 참조
- 담보 감정 승인, 선순위 권리, 근저당/질권 설정완료, 보험·보증 유효성
- waiver의 신청·독립승인·사유·범위·기간·개선계획·반복집중도

**최소 인수기준**

1. 필수 CP 또는 담보권 설정이 미완료면 booking 명령을 만들 수 없다.
2. 조건 변경은 원승인보다 낮지 않은 권한으로 재승인되고 이전 버전이 보존된다.
3. 문서 원본을 CLMS에 중복저장하지 않아도 EDMS 증빙과 해시·버전을 재현할 수 있다.

### 6.5 계정계 booking·익스포저·대사

**필요 기능**

- 승인과 실행을 `APPROVED → READY_TO_BOOK → BOOKING_PENDING → BOOKED/FAILED`로 분리
- transactional outbox, correlation ID, idempotency key, retry, dead-letter, 운영자 재처리
- 계정계 시설번호·실행번호·부분인출·한도재사용·상환스케줄·실행통지 참조
- 승인 전 예상 익스포저의 원자적 검사, 예약, 만료, 취소, 실행 전환
- 동일차주·기업집단 범위의 버전, 보증·난외항목·CCF·통화·환율·제외근거
- 승인–계정계–신용공여원장–한도–GL의 일별 및 사건기반 대사

**최소 인수기준**

1. 같은 요청을 반복해도 계정계 실행은 정확히 한 번만 성립한다.
2. 계정계 타임아웃 뒤 상태가 `성공인지 불명`으로 방치되지 않고 조회·재처리·대사된다.
3. 실행 성공 시 예약이 실제 익스포저로 전환되고, 실패·취소 시 정확히 해제된다.
4. 신규 금액을 합산한 법정·내부한도 초과는 승인 또는 실행 전에 차단된다.
5. 차이는 금액·통화·원인·책임자·SLA·조치상태까지 추적된다.

### 6.6 책무·감사·규칙·가격 통제

**필요 기능**

- `업무단계 → 위험 → 통제 → 수행자 → 2차 점검자 → 책임임원 → 증빙 → 결함 → 시정조치 → 보고` 연결
- 실제 사건시각(UTC), 은행 업무기준일, 원천 효력일, 수신시각을 분리
- actor, 조직, 위임, 세션/요청 ID, 실제 IP/채널, before/after, 사유, 규칙버전의 불변 감사
- Rule Registry를 모든 계산의 단일 정책 소스로 사용하고 효력일·지역·상품·고객군·승인상태를 버전화
- 대출금리 구성요소 allowlist와 2026-07-01 시행 금지·반영제한 법적비용 검증
- 연 2회 이상 자체점검의 모집단·표본·결과·예외·개선조치 증적

**최소 인수기준**

1. 같은 거래를 승인일 기준으로 재계산하면 당시 결과와 일치한다.
2. 대시보드·가격결정·자본최적화가 동일한 유효 RAROC 허들을 사용한다.
3. 금지 비용 또는 허용범위를 넘는 제한 비용을 가격 구성요소로 전달하면 저장·견적·승인이 모두 차단된다.
4. 핵심 변경의 감사기록 실패는 본 업무도 실패하고, 비핵심 실패는 outbox와 경보로 복구된다.
5. 책임임원 보고 수치에서 개별 거래·통제증빙까지 drill-down할 수 있다.

## 7. iM뱅크에 특화된 실무 기능

금융위원회는 2024년 iM뱅크의 시중은행 전환 인가에서 3년간 수도권·충청·강원 영업점 확대, 비대면·외부플랫폼 강화, 관계형금융 기반 중신용 중소기업·개인사업자 확대, 대구·경북 자금공급 지속을 제시했다. 동시에 내부통제 개선 이행실태의 주기적 당국 보고를 인가 부대조건으로 두었다. 2025년 지역재투자 평가에서도 iM뱅크는 시중·특수은행군 최우수 등급에 포함됐다.

따라서 iM 특화 기능은 단순한 지역 필터보다 다음 형태가 실무적이다.

### 7.1 PRM·분산영업–중앙심사 연결

- 현장방문, 고객접촉, 사업장·경영진 관찰, 제출자료 요청·수령·보완 이력
- 비대면/외부플랫폼 유입채널, 동의근거, 데이터 출처·신선도, 위변조·중복 확인
- 영업점/PRM에서 중앙심사로 넘기는 표준 hand-off packet과 누락 gate
- 영업 KPI와 승인률뿐 아니라 사후 연체·등급하락·예외·waiver 품질을 함께 평가

### 7.2 지역·생산적 금융 포트폴리오 가드레일

- 본점·사업장·고용·자금사용지역을 구분한 지역 귀속 근거와 변경이력
- 생산적/지역특화/포용금융 적격 코드, 판정근거, 정책·보증기관 연계
- 자금용도 승인과 실제 사용의 사후검증
- 공급액, 고객수, 금리만이 아니라 RWA, RAROC, 연체, NPL, 빈티지, 지역·산업 집중도를 병기
- 신지역·신채널 코호트의 승인률, override, 조기연체, adverse selection 모니터링

### 7.3 인가조건·책무 이행증거 패키지

- 내부통제 개선과제별 책임임원, 마일스톤, 통제수행, 표본점검, 결함, 시정, 재검증
- 영업점·비대면·외부플랫폼별 통제 적용률과 예외
- 보고시점의 point-in-time snapshot과 제출본 재현

이 세 기능은 iM의 “전국화”와 “지역기반”을 서로 상충하는 목표가 아니라 위험조정 성과로 함께 관리하게 한다.

## 8. CLMS의 현실적 시스템 경계

| 구분 | CLMS가 해야 할 일 | 하지 말아야 할 일 |
|---|---|---|
| 의사결정 | 신청, 심사, 등급·가격 참조, 승인경로, 조건, 예외, 판단 스냅샷 | 계정계 원장을 자체 대체 |
| 통제 | 전결·직무분리·gate·책무증거·감사·규칙버전 | 사내 IAM과 별도 사용자 생명주기 구축 |
| 고객확인 | AML/KYC 결과의 유효성 확인과 승인/실행 차단 | 제재검색·STR·AML 시나리오 엔진 복제 |
| 문서 | 체크리스트, 증빙 ID, 버전·상태·충족 검증 | EDMS 원본저장·전자서명 플랫폼 재구축 |
| 실행 | outbox, 요청상태, 멱등성, callback, 실패복구, 대사 | 입출금·이자계산·상환 원장을 직접 처리 |
| 회계·ECL | CLMS 판단근거와 중앙 결과의 reconciliation·승인·설명 | 중앙 IFRS 9/GL 엔진을 병렬 구축 |
| 감독·경영보고 | point-in-time 데이터마트와 거래·증빙 drill-down | 전사 규제보고 플랫폼 전체를 대체 |

핵심 원칙은 **데이터를 복제하기보다 책임을 명확히 연결하는 것**이다. 원천시스템 ID, 효력일, 조회시각, 상태, 버전, 품질, 대사결과를 CLMS가 보유하면 된다.

## 9. 권장 실행 순서와 통과 게이트

달력보다 통과 게이트로 관리하는 것이 안전하다.

### Gate 0 — 현재 신뢰성 바로잡기

- README의 Maker-Checker 과장 제거
- 승인 ID 충돌, 임의 단계전이, client-supplied actor, 권한 없는 중요 실행 차단
- 승인금리·기간 기본값과 UI 전송, 조건 JSON의 실제 사용 연결
- RAROC 허들 단일화, 마이그레이션 DB 경로 일치, 프런트엔드 CI 추가

**통과 조건**: 현재 재현된 P0 우회 사례가 모두 회귀시험에서 4xx로 차단되고 정상 다단계 시나리오는 성공한다.

### Gate 1 — 통제 커널

- 버전형 FSM·승인경로·위원회·직무분리
- 구조화된 승인조건/CP/waiver
- IAM policy adapter와 자원단위 권한
- 유효일자 Rule Registry, 완전한 감사·책무증거

**통과 조건**: 승인 1건을 당시 정책·사람·데이터·증빙으로 완전히 재현할 수 있다.

### Gate 2 — 은행 파일럿 통합

- AML/KYC, EDMS/전자서명, 계정계 booking, 신용공여·한도, 담보·보증 연계
- outbox·멱등성·retry·reconciliation 운영화
- 한 상품·한 조직·한정 고객군의 end-to-end 파일럿

**통과 조건**: 승인→조건충족→실행→원장·한도·GL 대사가 장애·재시도 시나리오에서도 일치한다.

### Gate 3 — iM 차별화와 운영전환

- PRM/중앙심사 hand-off, 지역·생산적 금융 가드레일
- 독립 여신감리, 데이터품질, 모델검증, ECL/GL 설명체계
- DR·복구훈련·관측성·보존·보안검증

**통과 조건**: 운영 SLA, RTO/RPO, 권한검토, 복구시험, 통제보고와 감독자료 재현을 실제 운영조직이 승인한다.

## 10. 지금 우선하지 않을 기능

- 통제되지 않은 상태에서 화면·차트·시뮬레이션 수를 더 늘리는 것
- 현재 규칙 기반 의견서 초안을 자동 승인형 AI로 확대하는 것
- CLMS 안에 코어뱅킹, AML, IAM, EDMS, 중앙 GL/ECL을 다시 만드는 것
- 실제 포트폴리오 비중이 확인되지 않은 PF·무역금융·난외상품을 한꺼번에 확장하는 것
- 향후 시행예정 정책을 현행 법정 hard stop으로 고정하는 것

## 12. 착수 전 은행이 결정해야 할 사항

다음은 코드만 보고 확정할 수 없으며 실제 은행 담당부서의 답이 필요하다.

1. 파일럿 상품·조직·고객군과 실제 승인경로·위원회·전결규정
2. 고객·기업집단·UBO의 권위 있는 원천과 유효일자 관리주체
3. IAM, AML, EDMS, 계정계, 담보, GL/ECL, 규제보고 시스템의 API·이벤트 계약
4. 승인조건·CP·waiver·담보권 완성의 상품별 필수규칙
5. 내부 가격 구성요소와 2026 법적비용 금지 통제의 책임부서·점검절차
6. 데이터 보존기간, 민감도, 마스킹, RTO/RPO, 장애·복구 승인기준
7. 실제 사용하는 통계/ML/AI 모델과 자동화 결정의 범위
8. PF·무역금융·보증 등 1차 릴리스에서 제외할 상품 범위

## 13. 최종 권고

다음 릴리스의 단일 목표를 **“통제된 승인 1건을 안전하게 실행하고 완전히 재현한다”**로 정하는 것이 가장 현실적이다.

이를 위해 우선 `FSM·다단계결재·세부권한·조건선행·booking/outbox·익스포저대사`를 하나의 얇은 end-to-end 흐름으로 완성한다. 그 뒤 iM 특화 PRM·지역/생산적 금융 기능을 얹으면 현재의 풍부한 분석 자산이 실제 영업·리스크·감사 가치를 만들 수 있다. 반대로 통제 커널 없이 분석 화면만 확장하면 데모의 인상은 좋아져도 은행 도입 가능성은 거의 높아지지 않는다.
